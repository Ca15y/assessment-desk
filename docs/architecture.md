# Prototype architecture

React/Vite is a static browser application. `src/domain.ts` defines the four schemas, examples and saved-project validation. `src/demand.ts` implements the isolated Demand Notice calculation. `src/pdf.tsx` renders project data and the demand calculation through React PDF. PDF-lib reads the generated page count and dimensions; PDF.js draws the actual first page for preview and reports when drawing completes. `src/App.tsx` owns only ephemeral browser state.

Generation is explicit after edits. Each generated result is tied to an exact project snapshot. A stale result cannot be downloaded. Multi-page results can be previewed to diagnose capacity but cannot be exported through the interface. All templates share the page-count and portrait A4 dimension export gate. Font size stays fixed at 9 pt for body text. Demand Notice uses a locally bundled OFL-licensed Noto Sans font only for the naira glyph absent from Helvetica; other text retains Helvetica.

The project format is discriminated by template, with strict version and layout fields. It contains data only, never HTML, JavaScript or replacement master-template code. An invalid import leaves the current form untouched. Amount inputs are strings; the two original templates preserve blank, NIL, zero and punctuation without arithmetic. Their version-1 saved projects remain compatible.

No network calls carry form data. The only requests are application/worker assets. There is no backend, authentication, analytics, service worker or automatic browser storage in this milestone. Save project explicitly downloads a JSON file, and Download PDF explicitly downloads the generated bytes.

Future template versioning and authentication should reuse these schemas and PDF components. A future backend may store approved templates and editor identities; it must not silently introduce taxpayer-record storage.

Demand Notice rule 1 parses principal to BigInt kobo. Penalty is ceiling(principalKobo × 10 / 100); interest is ceiling((principalKobo + penaltyKobo) × 21 / 100); total is the exact sum. Rates are fixed and applied once. There is no levy amount in this calculation. Blank or malformed input is rejected instead of becoming zero. The original input string remains in the project; formatted results are derived for display and PDF only.

Demand projects add `calculationVersion: 1` and the entered fields, including `managerName`, to the existing strict project envelope. No calculated totals or editable rates are stored or accepted on import. Reopening derives results with the explicitly versioned rule. Unknown calculation versions and injected outputs/rates are rejected; future formula changes must introduce a new rule version and preserve or explicitly migrate historic rules. No remote rate lookup or source-record storage is introduced.

Assessment Notice projects use the strict shared version-1 envelope with a separate template discriminator. Their `taxLiability` value remains a string, is repeated unchanged in the PDF narrative and payment instruction, and is never calculated. Template-specific editable code defaults are supplied on Clear form; imported values are retained.

Excel batch generation is restricted to Notes to Assessment and runs locally in browser memory. The prescribed workbook has the existing version-1 note marker and Instructions/Documents sheets; the parser resolves worksheet relationships, reads inline or shared text cells, rejects formulas and reports populated data rows using their spreadsheet row numbers. Legacy letter, demand and assessment workbook markers are rejected with guidance to use Single document. Workbook creation, batch preparation and exports enforce the note-only restriction. Technical ZIP and file-size bounds protect parsing; there is no fixed document-row cap. Batch preparation reuses the Note to Assessment project schema and the shared PDF renderer in row order. Each rendered PDF must have exactly one portrait A4 page. Any row validation, rendering or page-size failure discards partial bytes and keeps both exports disabled. A successful batch is merged in row order for combined PDF export or zipped as individual row PDFs. This processing is in-memory until the user explicitly downloads an export.
